# 成品檢驗（校機）條碼報工系統需求整理

更新日期：2026-10-27

## 1. 專案目標

以現有的組裝部門條碼報工系統為技術基底，建立一套供校機部門使用的成品檢驗報工系統。

沿用既有系統的 Flask、SQLite、條碼掃描、報表、Excel 匯出、權限、備份及稽核架構，但工作分派方式與資料模型必須依校機部門的實際流程重新設計。

本專案 GitHub repository：

- `https://github.com/Regan1994/inspection-reporting-barcode.git`
- 開發分支：`codex/final-inspection`

## 2. 組裝部門現行流程

組裝部門採用「事前分派」：

1. 員工先與主管確認要組裝哪些機台。
2. 員工到料車找到對應機台。
3. 組裝前通知助理。
4. 助理在系統中輸入組裝人員、機型、產品製號及數量。
5. 系統建立批次並列印 START／FINISH 條碼。
6. 因為工作在列印條碼前已確定，所以系統能預先知道誰負責哪些機台。

組裝部門的一個產品製號代表一台固定機台，而且正常情況下不會重複組裝。

## 3. 校機部門流程差異

校機部門採用「現場認領」：

1. 一台機台對應一張訂單。
2. 同一位客戶訂購十台機台時，會有十張不同訂單。
3. 每張訂單都有全系統唯一且不重複的訂單號碼。
4. 助理會預先在訂單上貼上 START／FINISH 條碼。
5. 助理建立及列印條碼時，尚不知道最後由哪位員工執行校機。
6. 員工完成手上的工作後，才拿下一張訂單，因此拿到訂單時才知道下一台要處理的機台。
7. 員工必須在開始工作時，透過自己的員工條碼認領該訂單。

因此，校機人員不能在訂單建立或條碼列印階段預先指定，必須在掃描 START 時才綁定。

## 4. 已確認的資料規則

### 4.1 訂單

- 訂單號碼是報工工作的主要識別。
- 訂單號碼在全系統中唯一，不允許重複。
- 一張訂單只對應一台機台及一次獨立的校機工作。
- 改單或重新檢驗時，一定會產生新的訂單號碼。
- 已完成的舊訂單必須保留，不得因改單而覆蓋或重新啟用。

### 4.2 機台製號

- 機台製號用來識別實體機台，但不是校機工作的唯一鍵。
- 訂單需保存四軸／五軸分類，供首頁、報表及 Excel 統計。
- 同一個機台製號可以出現在多張不同訂單中。
- 同一台機台可能因改單、改客戶或其他原因再次校機。
- 每次重新校機都以新的唯一訂單號碼建立新紀錄。
- 報表依製號查詢時，必須能看到該機台所有歷次校機紀錄。

範例：

```text
訂單 A001 → 製號 E27-01 → 王小明 → 已完成
訂單 A135 → 製號 E27-01 → 李小華 → 已完成
```

以上兩筆是合法且互相獨立的校機紀錄。

## 5. 校機人員主檔

每位校機人員預計包含：

- 唯一員工編號
- 員工姓名
- 唯一員工條碼
- 啟用／停用狀態
- 建立及更新時間

軸別不由使用者選擇，依規則自動判斷：機型名稱 F 或 M 開頭，或機台製號 S 開頭為五軸，其他為四軸；建立訂單時將判斷結果保存到訂單。

功能需求：

- 新增及管理校機人員。
- 系統自動產生可掃描的員工條碼。
- 支援列印單張或多張員工條碼。
- 停用人員不得再執行新的掃描報工。
- 停用不得刪除或破壞既有歷史紀錄。

## 6. 訂單建立與條碼列印

助理建立訂單時：

1. 輸入唯一訂單號碼。
2. 輸入或選擇該訂單需要的機型、機台製號等資料。
3. 不選擇校機人員。
4. 系統建立待校機訂單。
5. 系統產生該訂單專用的 START／FINISH 條碼。
6. 助理列印條碼並貼在紙本訂單上。

條碼必須識別「當次訂單」，不能只用機台製號識別工作。

## 7. 建議掃描流程

每次動作均採兩段掃描：

```text
開始：員工條碼 → 訂單 START
完成：員工條碼 → 訂單 FINISH
```

### 7.1 掃描員工條碼

- 系統辨識員工並在畫面顯示姓名及員工編號。
- 系統暫存這次操作的員工身分。
- 下一次必須掃描訂單 START 或 FINISH。
- 訂單條碼處理完畢後，立即清除暫存員工，避免共用電腦誤用上一位員工身分。

### 7.2 掃描 START

- 必須先有有效且啟用中的員工身分。
- 訂單狀態必須為待校機。
- 系統在此時才將訂單綁定給該員工。
- 記錄開始時間並將狀態改為校機中。
- 未先掃員工條碼、重複開始或無效訂單都必須拒絕。

### 7.3 掃描 FINISH

- 必須先掃描員工條碼。
- 訂單必須已開始且尚未完成。
- 預設只允許原認領員工完成該訂單。
- 記錄完成時間並將狀態改為已完成。
- 不同員工、完成早於開始或重複完成都必須拒絕並顯示原因。

## 8. 訂單狀態

建議狀態如下：

- 待校機：訂單已建立，但尚未有人掃描 START。
- 校機中：已由員工認領並開始作業。
- 已完成：已掃描 FINISH。
- 已取消：訂單取消，但歷史資料保留。

是否需要主管更換負責人、異常中止或重新開啟功能，尚待確認。

## 9. 畫面與名稱調整

預計調整：

- 系統名稱改為「成品檢驗報工系統」。
- 「組裝人員」改為「校機人員」。
- 「建立報工」改為「建立訂單」。
- 首頁統計改為待校機、校機中、已完成及已取消。
- 首頁掃描區顯示目前辨識到的員工及下一步操作提示。
- 「最近批次」改為「最近訂單」。
- 移除組裝批次、產品製號連號及五軸組裝階段等不適用功能。
- 保留機型管理，但機型、機台製號與訂單欄位的實際輸入方式尚待確認。

## 10. 報表與查詢

報表預計支援：

- 訂單號碼
- 機型
- 機台製號
- 校機人員
- 訂單狀態
- 四軸／五軸分類
- 開始時間
- 完成時間
- 校機耗時
- 每位員工的處理台數及完成統計
- Excel 匯出

依機台製號查詢時，必須列出該機台在不同訂單下的所有歷史校機紀錄。

## 11. 保留的既有功能

以下既有架構原則上保留並調整語意：

- Flask 本機離線系統
- SQLite 資料庫
- Code128 條碼
- USB HID 掃描器輸入
- 管理密碼
- 資料庫備份與還原
- 刪除前自動備份
- 掃描事件紀錄
- 稽核紀錄
- 報表與 Excel 匯出
- Windows 執行檔建置方式

新系統應使用獨立資料庫，例如 `instance/inspection.db`，不得讀取或影響組裝部門資料庫。

## 12. 必要驗證與測試

至少應驗證：

- 訂單號碼不可重複。
- 機台製號可以跨不同訂單重複。
- 員工編號及員工條碼不可重複。
- 停用員工不能報工。
- 未掃員工條碼不能開始或完成訂單。
- START 時正確綁定員工。
- FINISH 預設只能由原認領員工執行。
- FINISH 不能早於 START。
- 重複掃描不會重複寫入或破壞資料。
- 同一製號的多次校機歷史均可查詢。
- 報表篩選及 Excel 匯出結果正確。
- 備份、還原及稽核紀錄正常。

## 13. 尚待確認的需求

開始修改前仍需確認：

- 訂單建立時，除了訂單號碼外的必填欄位。
- 是否需要客戶名稱。
- 是否需要預計出貨日期。
- 機型採主檔選擇或直接輸入。
- 機台製號是否必填。
- 是否記錄改單或重新檢驗原因。
- 員工條碼及訂單條碼的實際標籤尺寸。
- 是否需要一次建立多張訂單或 Excel 匯入。
- 不同員工接手未完成訂單時的主管處理流程。

## 14. 建議實作階段

### 第一階段：資料模型與基本主檔

- 建立獨立資料庫設定。
- 建立校機人員、訂單及條碼資料結構。
- 建立資料驗證及狀態規則。
- 完成對應的單元測試。

### 第二階段：人員與訂單操作介面

- 校機人員管理及條碼列印。
- 訂單建立、列表及 START／FINISH 條碼列印。

### 第三階段：掃描狀態機

- 員工條碼辨識。
- 員工身分暫存及一次性使用。
- START 認領訂單。
- FINISH 完成與人員驗證。
- 掃描錯誤提示及稽核紀錄。

### 第四階段：報表、備份與驗收

- 報表篩選及員工統計。
- Excel 匯出。
- 備份、還原及刪除保護。
- 完整測試與現場掃描、列印驗收。

## 15. 修改控制規則

使用者要求：任何修改前都必須先取得明確同意。

因此後續工作必須遵守：

- 可以先進行唯讀檢查、分析及提出方案。
- 修改檔案、資料庫或設定前，先列出確切修改範圍並取得同意。
- Git commit、push、建立 Pull Request 或其他 GitHub 寫入操作前，也必須另外取得同意。
- 未取得同意時，不得自行修改或擴大工作範圍。
